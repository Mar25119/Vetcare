# RISK_REGISTER.md — Реестр рисков VetCare v2.1.0

## Матрица рисков

| ID | Риск | Признак / доказательство | Вероятность | Влияние | Уровень риска | Меры снижения |
|----|------|--------------------------|-------------|---------|----------------|---------------|
| **R-01** | **SQLite не масштабируется** | При нескольких одновременных записях возможна блокировка БД (sqlite3.OperationalError: database is locked) | Средняя | Высокое | 🔴 Высокий | Для production перейти на PostgreSQL. Добавить connection pooling. Использовать WAL-режим SQLite |
| **R-02** | **Нет HTTPS** | Трафик передаётся в открытом виде, пароли и сессии могут быть перехвачены | Высокая | Высокое | 🔴 Высокий | Настроить Nginx + Let's Encrypt. Включить SESSION_COOKIE_SECURE=True. Добавить HSTS-заголовки |
| **R-03** | **Пароль admin захардкожен** | Пароль admin123 создаётся автоматически при первом запуске, известен всем | Высокая | Высокое | 🔴 Высокий | Требовать смену пароля при первом входе. Добавить механизм принудительной смены через env-переменную |
| **R-04** | **Нет rate limiting** | Злоумышленник может проводить brute-force атаки на форму входа | Средняя | Среднее | 🟡 Средний | Интегрировать Flask-Limiter. Ограничить попытки входа (5 в минуту). Добавить CAPTCHA после 3 неудачных попыток |
| **R-05** | **Нет резервного копирования БД** | При сбое диска или ошибке пользователя данные будут потеряны безвозвратно | Средняя | Высокое | 🔴 Высокий | Настроить автоматический бэкап vetcare.db через cron (ежечасно). Хранить бэкапы в отдельном volume/облаке |
| **R-06** | **Нет мониторинга и алертинга** | При падении сервиса или ошибках 500 администратор узнает только от пользователей | Средняя | Среднее | 🟡 Средний | Интегрировать Sentry для отслеживания ошибок. Настроить healthcheck с алертами в Telegram/email |
| **R-07** | **Уязвимости зависимостей** | Используемые библиотеки (Flask, Werkzeug) могут содержать известные CVE | Низкая | Высокое | 🟡 Средний | Регулярно запускать `pip-audit`. Обновлять зависимости через Dependabot. Использовать фиксированные версии в requirements.txt |
| **R-08** | **Потеря сессии при перезапуске** | При перезапуске контейнера все пользователи выходят из системы (filesystem session) | Средняя | Низкое | 🟢 Низкий | Настроить Redis для хранения сессий. Использовать server-side sessions |
| **R-09** | **Отсутствие валидации на клиенте** | Некоторые формы не имеют клиентской валидации, что увеличивает нагрузку на сервер | Средняя | Низкое | 🟢 Низкий | Добавить HTML5-валидацию (required, pattern, type). Использовать JavaScript-валидацию для сложных полей |
| **R-10** | **Нет разграничения прав внутри ролей** | Все администраторы имеют одинаковые права, нет механизма делегирования | Низкая | Среднее | 🟢 Низкий | Внедрить систему permissions (CRUD по сущностям). Добавить роль "старший администратор" |

## Приоритеты снижения рисков

1. 🔴 **R-03** (пароль admin) — изменить механизм создания админа
2. 🔴 **R-02** (HTTPS) — настроить Nginx + SSL
3. 🔴 **R-01** (SQLite) — перейти на PostgreSQL для production
4. 🔴 **R-05** (бэкапы) — настроить автоматическое резервное копирование
5. 🟡 **R-04** (rate limiting) — интегрировать Flask-Limiter
6. 🟡 **R-06** (мониторинг) — настроить Sentry

## Вывод

Проект имеет **4 критических риска** (R-01, R-02, R-03, R-05), которые необходимо устранить перед промышленной эксплуатацией. Для demo-стенда и учебного проекта текущий уровень рисков приемлем, но требует документирования и плана mitigation.
